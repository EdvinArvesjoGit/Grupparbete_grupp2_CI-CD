## 2. Entry point migration

`ENTRY_POINT_CONTRACT.md` (90 lines, present in the repo — it is **not** empty,
though an earlier read attempt in this session returned nothing; a retry
returned full content) defines the target contract:

```python
def run(engine, korning_id: str | None = None) -> int
```

Current state of each module `src/run_pipeline.py` calls, verified by reading
the source and by running `python -m src.run_pipeline --dry-run` (output
reproduced below the table):

| Module | Entry point found | Takes `engine`? | Takes `korning_id`? | Returns row count? |
|---|---|---|---|---|
| `src/ingest/ledamoter.py` | `main()` (line 322) | No | No | No — no `return` statement, only `print()` |
| `src/ingest/voteringar.py` | `run(engine, korning_id=None)` (line 432) | **Yes** | **Yes** | **Yes** — returns `rows: int` |
| `src/transform/dim_ledamot.py` | `load_dim_ledamot()` (line 17) | No — calls `get_engine()` internally (line 22) | No | No — no `return` statement, only `print()` |

`--dry-run` output:
```
would call src.ingest.ledamoter.main()
would call src.ingest.voteringar.run(engine, korning_id)
would call src.transform.dim_ledamot.load_dim_ledamot()
```

`src/run_pipeline.py`'s `_resolve_callable()` (lines 73-95) already implements
the fallback chain (`run` → `main` → any `load_*`), and `run_step()` (lines
119-150) logs a warning whenever a step doesn't expose `run`. So the
orchestrator runs today despite the migration being incomplete — this is by
design, per the docstring at `run_pipeline.py:76-81` ("delete it once all
three expose run()").

**Consequence of the incomplete migration** (observation, not stated
explicitly in either doc): because `ledamoter.main()` and
`dim_ledamot.load_dim_ledamot()` do not accept `engine`/`korning_id`, they
each build their own engine (`get_engine()` — same cached instance, so no
practical difference there) and, in `ledamoter.py`'s case, generate their own
`korning_id` internally (`uuid4()` at line 324) rather than using the run id
the orchestrator generated for the whole pipeline run. Neither module calls
`log_step`, so neither writes a row to `ops.load_log` when run through the
orchestrator — only `voteringar.run()` does. The one-`korning_id`-ties-every-step
traceability that `run_pipeline.py`'s module docstring (lines 3-10) and
`DATABASE.md`'s audit-column rationale (line 71) describe does not currently
hold for two of the three steps.

`voteringar.py` is further along than `ENTRY_POINT_CONTRACT.md`'s
per-module notes (lines 62-79) describe: the contract doc says it "builds its
own psycopg connection" and suggests moving `INGEST_MODE`/`KORNING_ID`
module-level globals into the `run()` signature. The current file already
uses `engine.connect()` (line 454, SQLAlchemy, not raw psycopg) and has no
`INGEST_MODE` global at all — only `KORNING_ID` is read, and only inside
`main()` (line 465) as the documented fallback default, matching the
contract's guidance ("keep reading the env var as the default in
`__main__`"). The contract document appears to describe an earlier state of
this file.

## 6. CI

### `.github/workflows/ci.yml`

**Job `lint-and-test`** — triggers: every `pull_request`, every push to `main`.
Steps: checkout → `setup-python 3.11` → `pip install -r requirements-dev.txt`
→ `ruff check .` → `ruff format --check .` → `pytest tests -m "not integration"`.
Fails on: any ruff lint violation, any formatting difference, any of the 46
non-integration test failures, or a `pip install` failure.

**Job `integration`** — same triggers, runs alongside `lint-and-test`. Spins
up a `postgres:16` service container (`POSTGRES_DB=riksdag_test`, user/password
`postgres`/`postgres`), sets `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD`
env vars (matching what `config.py` reads — the workflow's own comment at
lines 48-49 calls out that a `DATABASE_URL` var would silently do nothing).
Steps: checkout → setup-python → install deps → run `sql/00_init.sql` then
every `sql/[1-3]*.sql` file in order with `ON_ERROR_STOP=1` → re-run
`sql/00_init.sql` again to check idempotency → `pytest tests -m integration -v`.
Fails on: any SQL error in any DDL file (hard stop via `ON_ERROR_STOP=1`), a
non-idempotent `00_init.sql`, or any of the 8 integration test failures.
`sql/checks/*.sql` are not run by this job (they are ad-hoc/manual, not part
of the numbered DDL sequence it globs).

**What could pass without actually testing anything real:**
- `requirements-dev.txt` installs `requirements.txt`, which does not include `fastapi` or `pydantic`. No test file imports `reports/riksdag/rikdagen_api.py` or `reports/riksdag/schemas.py`, so neither CI job ever imports them — a broken or absent report layer (see §7) produces no CI signal at all, green or otherwise.
- `ruff check .`/`ruff format --check .` are static — they would pass on `reports/riksdag/riksdagen.py` (an empty file) and on the FastAPI stub route that always `return []`, without indicating those aren't functional.
- The `integration` job's own DDL step now creates `stg.votering_summary` and runs against a fresh, empty database each time; it never invokes any ingest/transform module, so a green integration run only proves the DDL applies cleanly and the four hand-written assertions in `test_database_integration.py` hold — it does not prove `ledamoter.py`, `voteringar.py`, or `dim_ledamot.py` load correct data (see §5).

### `.github/workflows/test-dim-ledamot.yml`

Triggers only on `push`/`pull_request` that touch
`src/transform/dim_ledamot.py`, `tests/test_dim_ledamot.py`,

This job is a strict subset of what `ci.yml`'s `lint-and-test` job already
runs (that job runs the entire `tests/` directory, `test_dim_ledamot.py`

change to `sql/30_dw_dimensions.sql` (which defines `dw.dim_ledamot`) does not
trigger it — though that gap is arguably moot since this workflow never talks
to a database anyway. As with `ci.yml`, a green run here says nothing about
`load_dim_ledamot()` itself (see §5's note on the same gap).
